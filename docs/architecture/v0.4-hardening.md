# AMRGuard v0.4.0 — Integration & Reliability Hardening

## Purpose

v0.4 turns the pitch MVP into a cleaner integration-ready foundation. It does not claim live connectivity to e-Buzima, RMS/eLMIS, pharmacy vendors, or insurers.

## Reliability controls

- External prescription ingestion is idempotent on the external prescription ID.
- Dispensing supports an optional idempotency key to prevent duplicate transactions during retries.
- Request IDs are returned on every HTTP response.
- Integration endpoints can be protected with `INTEGRATION_API_KEY`.
- QR/OTP credentials are stored as hashes, expire after 10 minutes in the demo, and can be revoked.
- Dispensing requires a valid prescription credential and checks pharmacy, batch, antibiotic, authorization, expiry, and stock.
- Batch events retain source system and transaction references.
- Patient data is represented as a reference rather than a duplicated clinical record.
- CORS is configurable through `ALLOWED_ORIGINS`.

## Production integration path

1. Obtain the approved external API/interface specification.
2. Implement or configure the corresponding adapter under `integrations/`.
3. Map the external contract into AMRGuard's canonical models.
4. Use the institution's approved service-to-service authentication.
5. Run contract, security, load, and interoperability tests in a sandbox.
6. Obtain required governance/clinical approval before production use.

## FHIR readiness

The core model is intentionally compatible with common FHIR concepts such as MedicationRequest and MedicationDispense, but this repository does not claim conformance certification. A reviewed FHIR mapping should be created against the target Rwanda interoperability specification before production integration.

## Clinical rules

The demo rule set is illustrative only. Production rules must be derived from approved local clinical guidance and governed by the responsible clinical/AMR authority. Hard-block thresholds should not be deployed solely from this prototype.
